# eMule 26.11.38 修复与验证报告

日期：2026-11-05 ｜ 验证设备：fnos-test（192.168.1.13）｜ 验证版本：26.11.38

## 一、首页「最近日志」时间与内容粘连（用户反馈）

**原因**：概览的日志行只有「时间」和「正文」两个节点，没有日志页那个带左右外边距的级别徽标。
日志页的间距其实是徽标的 `margin-right:12px` 提供的，概览没有徽标，两段文字直接贴在一起。

**修复**：新增相邻兄弟选择器 `.logline .t + .m { margin-left: 12px }`，只在正文紧跟时间时命中；
日志页中间隔着徽标，这条不匹配，原来的 10/12 间距不受影响。手机端（≤640px）正文换到第二行时清零，不产生缩进。

| 场景 | 实测间距 |
| --- | --- |
| 概览桌面（1440） | 12.00px |
| 概览手机（390，正文第二行） | 缩进 0.00 |
| 日志页桌面 | 时间→徽标 10.00 ／ 徽标→正文 12.00（与修复前一致） |
| 日志页手机 | 时间→徽标 10.00 ／ 正文缩进 0.00 |

## 二、真实任务下载验证

用 Debian 13.6.0 官方 netinst ISO（开源镜像）跑完整链路：

- 搜索 → 97 条结果；加入 → 列表出现；状态流转 waiting → downloading → waiting → downloading
- 速度 15–44 KB/s，done 0 → 1,003,498 → 2,017,280 → 3,062,101
- Temp 生成 `001.part`(787,988,480B) + `.part.met`(1579B) + `.bak`，`/proc/<pid>/fd` 确认引擎持有句柄；
  `stat` 分配块 4096×512=2,097,152B 与 done 吻合
- 删除（连数据）后列表归零，Temp/Incoming/deleted 全部清空
- **下载过程零报错**：期间只有 4 条与下载相关的日志（两条 adding link、两条 Downloading）

### 测试中发现并修掉的两个真缺陷

1. **详情页「来源」标签页永远空白**。两层原因：客户端数据在容器子节点里（只看顶层就丢掉）；
   且引擎的增量回包只在一条连接的头一次给全量，之后只回编号。现在展开容器解析，
   并按连接累积每个编号最近一次的完整信息、以本次出现的编号为准收敛，连接重建时清空。
   实机验证：详情接口返回 2 条来源（qeqhkp@79.154.81.25:21663、Mularr@64.42.180.114:53202）。
2. **「添加时间」取的是最后一次收到数据的时刻**，会一直往后跳，默认排序跟着抖。
   引擎侧没有添加时间字段，改为面板记录首次见到任务的时刻（`added.json`），删除任务时清理。

## 三、日志体检

| 项目 | 结论 |
| --- | --- |
| traceback | panel.log 0 处、amuled.log 0 处 |
| EC 协议错误 | 0 |
| 重连风暴 | 不成立（82 次断开里唯一密集段是手动切服 6 次，其后 64 小时零复发） |
| 线程/fd 泄漏 | 无（amuled 13 线程/27fd/RSS 33.9MB 稳定） |
| 磁盘/权限 | 正常 |
| panel.log 非 info 行 | 51 行 / 5 类，3 条 error 全是当版已修的代码缺陷留下的历史记录 |

真正的问题不是「错误」，而是**日志被噪声淹没**：

- UPnP 事件块占引擎日志 **96.1%**（19,135 个事件 × 8 行），日志页可见窗口被压到 10.7 分钟，
  概览「最近日志」六条全是 `Key: 42xx`／`Property list:`；
- `amuled.log` **没有任何轮转**，实测 101 MB/月；
- 「GitHub API 不可用」每小时一条 warn，占 panel.log 全部 warn 的 46/49，真正的告警被淹没。

**26.11.38 处理**：UPnP 八行折成一条摘要 + 连续重复合并（末尾缀「连续 N 次」）、
引擎日志启动前按 8 MB 轮转、403 只在「掉到备用源／恢复回 API」两个切换点各记一条 info。

实机验证：概览最近日志已显示 `Universal Plug and Play: … 网关状态事件（… ）（连续 4 次）`，
200 条日志里只剩 6 条 UPnP（原来会占满整个窗口）；`amuled.log.1` 已生成（9.6 MB 滚走）。

## 四、诊断接口的一处隐患（未改，建议排期）

`/api/diagnostics` 报的公网 IP 是 103.156.242.229，而路由器 IGD 与 ifconfig.me 都返回 180.113.236.57。
原因是探测源顺序取第一个成功，这台机器的分流规则让不同站点走不同出口；`cgnat` 判定建立在这个错值上。
建议改成至少两个源一致才采信，不一致就落 warn。

## 五、环境事实（避免误判）

- 路由器 4662/TCP 与 4672/UDP 映射给的是 192.168.1.10（生产机），不是测试机 .13。
  所以测试机拿 Low ID 是必然的，不是缺陷；诊断卡建议「转发到 .13」在测试机上会和现有映射撞车。
- 测试机 `settings.engine.upnp=true`（默认应为 false），在这台机器上只买到了每分钟 40–120 行日志。
- 下载中的分块在 `/vol1/@appshare/fn-emule/Temp`，不是 `var/amule/Temp`（后者全程为空，容易误判）。
