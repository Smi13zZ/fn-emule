# 26.11.44 测试机验证报告

测试环境：fnos-test（192.168.1.13），面板 26.11.44，aMule 2.3.3，2026-11-06 16:xx CST。
**全程只在测试机上做，未触碰生产机。**

## 一、修了什么

| 反馈 | 根因 | 修法 |
| --- | --- | --- |
| 通知通道删不掉 | 前端发 `remove:true`，后端只认 `delete:true` → 删除请求被当成「新增通道」走类型校验，报「未知的通知通道类型：(空)」 | 后端同时接受 `remove` / `delete` / `action:"delete"` / 直接 DELETE |
| 共享文件夹上千个文件只扫到几百个 | aMule 的 `AddFilesFromDirectory()` **只扫目录顶层，从不递归** | 面板写 `shareddir.dat` 前把目录树摊平 |
| 没有任何提示 | 引擎只在「顶层一个文件都没有」时才留日志 | 共享页加「扫描范围：N 个共享目录 → M 个待扫目录」 |
| （附带发现）重扫会卡死面板 | `EC_OP_SHAREDFILES_RELOAD` 在 aMule 侧同步跑完整轮扫描，EC 串行连接被堵 | 发完就走，迟到的 NOOP 由计数器吞掉 |

## 二、根因证据（aMule 2.3.3 源码）

`SharedFileList.cpp` 的 `CSharedFileList::AddFilesFromDirectory()`：

- 用 `CDirIterator SharedDir(directory)` 只遍历**当前这一层**
- 遇到子目录 `fullPath.FileExists()` 为 false → `continue`（静默跳过，连 debug 日志都不写）
- 全函数没有任何递归调用

对比实验（同一批数据，只改 shareddir.dat）：

| shareddir.dat | 共享文件数 |
| --- | --- |
| 只有根目录 2 行 | **9** |
| 摊平后 44 行 | **118** |

## 三、修复后实测

**共享目录（3 层嵌套 / 6×6×6 = 216 个文件）**

- 配置 2 个共享目录 → 摊平成 44 个待扫目录
- 深目录里的文件被收录：**216 / 216**
- 共享总数从 8 涨到 **224**
- 共享页显示：`扫描范围：2 个共享目录 → 44 个待扫目录`

**重扫不再卡死**

| 指标 | 修前 | 修后 |
| --- | --- | --- |
| `POST /api/shared/reload` | 10 秒超时失败 | **0.20 秒返回** |
| 重扫期间 `/api/overview` | 排队阻塞 | 0.25 秒正常 |
| 扫描结束后各接口 | — | 0.24～0.30 秒 |

**通知通道删除**

- 前端实际发法 `{id, remove:true}` → 删除成功，通道从列表消失
- `{id, delete:true}` → 同样可以删
- 测试结束后测试通道已清理干净

## 五、安全上限

- 目录数上限 4000 条（`SHARED_SCAN_MAX_DIRS`）
- 深度上限 8 层（`SHARED_SCAN_MAX_DEPTH`）
- 不跟随符号链接，防环形目录
- 到上限时 `/api/shared` 的 `scan.truncated` 为 true，页面标注「目录过多已截断」
- 单条路径不存在照常写进清单，由引擎自己报错，不因为一条写错就让整份配置失败
