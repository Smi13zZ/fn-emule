# 26.11.51 修复与验证报告：共享文件规模问题

- 修复日期：2026-11-08
- 版本：**26.11.51**（基于 26.11.50）
- 触发来源：社区反馈「共享扫描条数一直不动」+ 日志里「速度采样失败（引擎不可用）：引擎响应超时」
- 验证环境：`fnos-test`（192.168.1.13），amuled 2.3.3

---

## 一、根因（比最初判断的更底层）

最初以为是「重扫把面板堵死」。实测推翻了它：重扫期间 aMule 的 UPnP 事件照常每秒在写，
**主循环并没有死**（04:43–04:52 每分钟 18–26 条）。真正的问题是三条链叠加：

### 根因 1：共享列表取数是 O(N²)（主因）

面板取共享列表用 `EC_OP_GET_SHARED_FILES`。aMule 侧的实现是

```cpp
for (uint32 i = 0; i < theApp->sharedfiles->GetFileCount(); ++i)
    const CKnownFile *cur_file = theApp->sharedfiles->GetFileByIndex(i);   // ExternalConn.cpp:644
```

而 `GetFileByIndex` 内部是

```cpp
CKnownFileMap::const_iterator pos = m_Files_map.begin();
std::advance(pos, index);          // SharedFileList.cpp:568-569
```

`m_Files_map` 是 `std::map`，`std::advance` 对它是**线性**的。
于是 N 个文件要前进 N²/2 次。

实测曲线（旧版，真实数据）：

| 共享文件数 | `GET_SHARED_FILES` 耗时 |
|---|---|
| 10 856 | 4.99 s |
| 20 102 | **14.97 s** |

面板的 HTTP 预算是 `DATA_TIMEOUT = 15.0`。**20 102 那一档直接撞满上限变成 504**，
而且这个调用占着唯一那条 EC 连接，于是速度采样（8 s）、通知轮询（10 s）、
概览、共享页全部排队超时 —— 用户看到的「引擎响应超时」就是这么来的。

### 根因 2：新文件要一个个算哈希，而页面不刷新

aMule 把新共享文件交给 `CThreadScheduler` 逐个算 MD4+AICH。
调度器源码注释写明「only a single task is allowed to proceed at any one time」，
并发度**硬编码为 1**，没有任何配置项。所以 6 万个文件要排很久。

而面板这边：`reloadShared()` 发完命令后 `setTimeout` **只等 2 秒**拉一次列表，
之后再也不管了（`app.js` 原 `refresh()` 里明写共享列表 static、reload on demand）。
于是用户看到的就是「点了没反应 / 数字一直不动」。

### 根因 3：保存设置会把摊平清单打回原形

面板为了让引擎认得子目录，会把目录树摊平成一份清单写进 `shareddir.dat`。
但 `EC_OP_SET_PREFERENCES` 在引擎侧会：

1. 把 EC 传来的目录列表塞进 `glob_prefs->shareddir_list`（ECSpecialMuleTags.cpp:509-513）
2. 立刻 `glob_prefs->Save()`，而 `Save()` 会**整个重写** `shareddir.dat`（Preferences.cpp:1477-1482）
3. 下次 `FindSharedFiles()` 第一步就是从这个文件重读（SharedFileList.cpp:320）

所以只要通过 EC 发一次 `shared_dirs`，摊平清单就被覆盖成未摊平版 ——
共享文件又「只剩顶层几个」，26.11.44 的修复被悄悄抵消。

## 二、改了什么

| # | 改动 | 位置 |
|---|---|---|
| 1 | 共享列表改走 `EC_OP_GET_UPDATE`（O(N)，遍历编码器表，没有线性前进） | `core/ec.py` `shared_files_fast()` |
| 2 | `GET_UPDATE` 收敛成**唯一发送点**，避免多个调用方互相推进增量状态 | `core/ec.py` `_update_snapshot()` |
| 3 | 共享目录**完全不经 EC**，只写清单 + 单发 RELOAD | `core/service.py` `apply_prefs()` |
| 4 | 改共享目录不再要求重启引擎，当场重扫 | `core/service.py` / `emulepanel.py` |
| 5 | 重扫改成后台任务 + 可查询进度 | `core/service.py` `_start_shared_scan()` |
| 6 | 共享列表缓存 + stale-while-revalidate（引擎忙时先给旧数据） | `core/service.py` `shared()` |
| 7 | 引擎调用分优先级 + 后台合并（队列有界） | `emulepanel.py` `EngineBox` |
| 8 | 前端扫描期间轮询进度，条数边扫边涨 | `web/js/app.js` / `index.html` / `i18n.js` |
| 9 | 新增 `/api/shared/progress`，扫描状态单独一条轻量路由 | `emulepanel.py` |

### 顺带修掉的两个隐藏 bug

- `_update_cache` 初始化时只有 `files/clients/servers` 三个键，`shared` 是懒创建的，
  于是**重连时不会被清空**，共享列表会残留已不属于本机共享的陈旧条目。
  现在 `_reset_update_cache()` 四个键一起清。
- 缓存命中时把整个条目 `{at, payload}` 当响应体返回，前端读 `data.items` 拿到 undefined，
  **页面条数恒为 0**（只有 `force=1` 的请求是对的，非常隐蔽）。
  现在 `_shared_cache_get()` 只返回 payload。

### 3.2 重扫期间不再 504（对照组）

| 场景 | 旧版 | 新版 |
|---|---|---|
| 重扫期间 `/api/shared` | 连续 504 @15.00 s | **25/25 全部 200**，最差 7.3 s（首请求等 EC 重连的瞬态），稳定态 9–13 ms |
